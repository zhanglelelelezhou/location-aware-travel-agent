# 面试问题库（持续更新）

## 1. 这个项目为什么需要 Agent，普通 RAG 不行吗？

RAG 解决的是“从知识库取什么上下文”，但旅行请求还需要决定是否查 POI、天气、路线或翻译，并根据工具结果继续行动。Agent 负责决策和执行闭环，RAG 只是其中一个知识工具。如果问题只是文档问答，我不会使用 Agent。

## 2. 为什么用 LangGraph，不直接用 LangChain Agent？

我需要有界重试、显式状态、未来的人工确认节点以及可复现的执行路径。状态图比自由循环更容易测试、控制成本和定位错误。代价是流程设计工作更多，开放性也更低，但这符合旅行助手对可靠性的要求。

## 3. 为什么不做多 Agent？

目前没有证据证明多 Agent 能提高任务成功率。单 Agent 加专业工具更简单、延迟更低、调试更容易。我会先用失败案例判断问题是否来自上下文冲突或任务分解，再决定是否拆分。多 Agent 是待验证的架构选项，不是项目卖点。

## 4. 如何防止模型调用错误工具？

计划采用结构化输出、严格参数模型、工具白名单和执行前校验；有副作用的工具必须加入人工确认。评测集中还要覆盖相似工具、缺失参数、提示注入和外部服务异常。

## 5. 外部地图或模型服务失败怎么办？

adapter 将超时、限流和响应格式错误归一化；状态图只允许有限次重试，然后降级或明确告诉用户不可用，不让模型编造实时信息。Mock fixture 用于 CI，真实服务使用契约测试和少量集成测试。

## 6. 怎么评价 Agent 做得好不好？

不能只看回答是否“像对的”。至少分层统计：意图识别、工具选择、参数正确率、工具执行成功率、最终任务成功率、引用正确率、P95 延迟和成本。规则可判断的部分使用确定性 evaluator，主观回答质量才使用模型裁判，并抽样人工复核。

## 7. 你在实习项目和这个开源项目中分别做了什么？

回答时严格分开：实习部分根据真实经历说明；开源部分可以明确说是自己重新设计的工程化版本，包括状态图、统一工具接口、评测、测试和部署。不要暗示公司采用了作品集里的全部架构。

## 8. 当前版本最大的不足是什么？

LLM Planner 的接口、结构化输出、修复和降级已经完成自动化测试，但还没有接入真实模型跑完固定评测；工具也仍是 fixture。因此当前只能证明控制流和安全边界，不能宣称真实模型已经提升泛化能力。下一步要用同一批用例测量收益、延迟和成本，然后再接入真实 MCP 工具。

## 9. 为什么模型输出错误时不一直重试？

重试次数越多，延迟和成本越不可控，也可能重复产生同类错误。我只允许一次带验证错误的定向修复；仍不合法就走规则降级，并在 trace 中保留失败原因。这样能给系统可靠性和成本设置清晰上界。

## 10. 为什么要保留一个效果较差的规则基线？

没有基线就无法证明 LLM 带来的收益是否值得额外延迟和成本。规则版本还能用于 CI、离线开发和供应商故障时的降级。评测中的语义改写用例会主动暴露关键词规则的上限，而不是只挑规则能通过的 Demo。

## 11. 既然有规则降级，评测会不会被“兜底成功”美化？

会有这种风险，所以报告把完整任务通过率和原生 LLM 通过率分开，并单独统计 fallback_count。由规则兜底通过的样本不会算作模型原生成功。这样可以同时评价用户最终体验与模型本身的规划能力。
