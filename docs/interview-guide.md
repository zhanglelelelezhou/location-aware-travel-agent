# 面试问题库（持续更新）

## 1. 这个项目为什么需要 Agent，普通 RAG 不行吗？

RAG 解决的是“从知识库取什么上下文”，但旅行请求还需要决定是否查 POI、天气、路线或翻译，并根据工具结果继续行动。Agent 负责决策和执行闭环，RAG 只是其中一个知识工具。如果问题只是文档问答，我不会使用 Agent。

## 2. 为什么用 LangGraph，不直接用 LangChain Agent？

我需要有界重试、显式状态、未来的人工确认节点以及可复现的执行路径。状态图比自由循环更容易测试、控制成本和定位错误。代价是流程设计工作更多，开放性也更低，但这符合旅行助手对可靠性的要求。

## 3. 为什么不做多 Agent？

目前没有证据证明多 Agent 能提高任务成功率。单 Agent 加专业工具更简单、延迟更低、调试更容易。我会先用失败案例判断问题是否来自上下文冲突或任务分解，再决定是否拆分。多 Agent 是待验证的架构选项，不是项目卖点。

## 4. 如何防止模型调用错误工具？

我使用结构化输出、严格参数模型、工具白名单和执行前校验；模型给出合法候选计划后，还要经过确定性策略层。有副作用的预订在确认前禁止执行，行程计划必须包含 POI 与天气工具。策略补正会进入 trace，避免把代码兜底伪装成模型能力。

## 5. 外部地图或模型服务失败怎么办？

adapter 将超时、限流和响应格式错误归一化；状态图只允许有限次重试，然后降级或明确告诉用户不可用，不让模型编造实时信息。Mock fixture 用于 CI，真实服务使用契约测试和少量集成测试。

## 6. 怎么评价 Agent 做得好不好？

不能只看回答是否“像对的”。至少分层统计：意图识别、工具选择、参数正确率、工具执行成功率、最终任务成功率、引用正确率、P95 延迟和成本。规则可判断的部分使用确定性 evaluator，主观回答质量才使用模型裁判，并抽样人工复核。

## 7. 你在实习项目和这个开源项目中分别做了什么？

回答时严格分开：实习部分根据真实经历说明；开源部分可以明确说是自己重新设计的工程化版本，包括状态图、统一工具接口、评测、测试和部署。不要暗示公司采用了作品集里的全部架构。

## 8. 当前版本最大的不足是什么？

天气和 POI 已接入真实开放数据并支持 MCP，知识检索也有官方来源快照和引用，但翻译仍是 fixture。Planner 只有 20 条开发集和 20 条留出集，知识检索也只有 6 个段落。当前稠密/RRF 盲测只有 12 条正例和 8 条难负例，且混合方案没有改善 Hit@3 或拒答。DeepSeek + 策略层的单次留出结果也不能衡量模型波动。下一步要扩大知识库并建立新的测试集做 Rerank 对照，同时补充 Planner 重复评测和工具参数准确率。

## 9. 为什么模型输出错误时不一直重试？

重试次数越多，延迟和成本越不可控，也可能重复产生同类错误。我只允许一次带验证错误的定向修复；仍不合法就走规则降级，并在 trace 中保留失败原因。这样能给系统可靠性和成本设置清晰上界。

## 10. 为什么要保留一个效果较差的规则基线？

没有基线就无法证明 LLM 带来的收益是否值得额外延迟和成本。规则版本还能用于 CI、离线开发和供应商故障时的降级。评测中的语义改写用例会主动暴露关键词规则的上限，而不是只挑规则能通过的 Demo。

## 11. 既然有规则降级，评测会不会被“兜底成功”美化？

会有这种风险，所以报告把完整任务通过率和原生 LLM 通过率分开，并单独统计 fallback_count。由规则兜底通过的样本不会算作模型原生成功。这样可以同时评价用户最终体验与模型本身的规划能力。

## 12. 为什么第一次接入 LLM 后反而比规则版本低？

第一次评测只有 30%，但错误分析发现多数扣分来自标注复刻了规则实现：所有餐厅请求都被要求翻译、互不依赖的工具被强制规定顺序。我的处理不是直接修改分数，而是保留初始报告，回到产品需求重新定义主任务意图、工具集合和约束，再用同一批已保存预测离线重评分。最终规则为 55%，DeepSeek 为 85%。这次经历说明评测设计本身也必须接受审查。

## 13. 为什么不用 Prompt 把行程漏工具继续调到 100%？

原来的三个失败都是模型已经识别 itinerary，却漏掉业务规定的必选工具。这属于确定性业务约束，不应依赖模型每次记住。我让 LLM 负责语义理解，再由策略层补齐或拒绝不完整计划，并把补正写入 trace。新一轮开发集达到 95%，没有为了追逐 100% 而隐藏新的翻译歧义。

## 14. 你怎么证明不是在开发集上过拟合？

我在首次真实调用前冻结了另一组 20 条中英文用例，并把文件 SHA-256 写入报告和测试。规则在留出集为 50%，DeepSeek + 策略层为 85%。首次运行后我没有根据 3 个失败修改 Prompt、策略或标注，所以这组结果保留了真正的留出意义。

## 15. 为什么留出集不是 100%，你会怎么处理失败？

两个失败来自次级意图集合的标注边界，一个来自“问路句子”是否算已提供翻译文本。我的第一步不是立刻调 Prompt，而是建立错误分类并让产品契约先回答：次级意图是否影响工具选择、抽象短语能否直接生成。确定契约后应创建新的开发样本迭代，原留出集继续冻结；最终再用新的测试集验证，而不是反复消费同一留出集。

## 16. 接入真实天气 API 时遇到了什么问题？

第一次输入中文“东京”时，Open-Meteo 地理编码返回了中国江苏的同名地点。如果只看 HTTP 200 和字段完整性，这个错误会静默进入最终回答。我的修复不是硬编码城市别名，而是让位置感知设备优先传经纬度；文本搜索仅作为回退，无法可靠消歧时明确失败。工具输出同时保留 `resolved_location`、时区、来源和 `resolution_method`，方便线上审计。

## 17. 为什么真实天气失败时不让模型自己猜？

天气属于时效性事实，模型参数知识不能替代实时数据。adapter 会把超时、HTTP 错误和非法响应归一化，状态图最多重试一次；仍失败时明确告诉用户不可用，并把错误写入 trace。这比给出流畅但可能错误的天气更符合旅行场景的可靠性要求。

## 18. POI 搜索如何防止查询注入和数据抓取失控？

LLM 不能生成任意 Overpass QL。adapter 只接收类别白名单、可信坐标和有上限的半径/结果数，再由代码生成查询；用户文本和偏好不会直接拼进查询。超时固定为 10 秒，输出最多请求 60 个元素、本地最多返回 10 个。公共实例只用于低频演示，生产环境会使用缓存、配额和自建或商业服务。

## 19. 怎么证明推荐真的符合“纯素”偏好？

不能靠地点名字或模型常识猜测。当前实现要求 OSM 的 `diet:vegan=yes` 或 `only` 标签，才会把该地点作为纯素匹配返回。清真、素食和无麸质同理。对于“安静”“适合约会”等当前数据无法证明的偏好，系统会保留候选但标记为未验证，并在回答中明确说明，避免把检索召回误写成事实。

## 20. 为什么要做 MCP，普通函数调用不够吗？

项目内部调用当然可以直接使用 Python 接口，但这会把工具绑定在一个 Agent 实现里。MCP 让兼容 Host 通过统一协议发现工具、读取 Schema 和调用结构化结果，天气与 POI 能被其他 Agent 复用。我的实现没有为了 MCP 重写业务逻辑：wrapper 只负责协议适配，adapter 和输出模型与 LangGraph 共用。

## 21. 怎么证明 MCP Server 真的能工作？

我没有只测试被装饰的 Python 函数。测试使用官方 `Client(server)` 完成协议协商、`tools/list`、Schema 与 annotations 检查以及 `tools/call`；另一个测试通过 stdio 启动真实子进程并发现两个工具。Agent 集成测试还会让 LangGraph 的计划经过 MCP Client 执行，并验证多工具计划复用一个会话。非法类别和超大半径会在进入 adapter 前返回 MCP 错误结果。

## 22. MCP 工具标记为只读就安全吗？

不是。annotations 是给 Host 和模型的规划提示，不是安全边界。真正的边界仍在服务端：坐标范围、类别白名单、查询半径、返回数量、超时和供应商错误都由 Schema 与 adapter 强制执行。stdio 的边界是本地启动进程；Streamable HTTP 上线时还必须增加认证、TLS、Host 校验和速率限制。

## 23. 内部已经能直接调用 adapter，为什么还让 Agent 走 MCP Client？

直连路径用于低延迟基线和快速定位领域逻辑；MCP 路径验证工具能被真实协议消费，并让 Agent 与工具进程、语言和部署位置解耦。两条路径复用相同 Planner、策略和输出契约，因此可以做公平对照。实现上按一次执行计划建立会话，而不是每个工具启动一次进程；纯本地计划不建连接，MCP 故障也不阻塞本地工具。代价仍包括协议序列化和连接开销，所以不会宣称 MCP 一定比直连更快。

## 24. 为什么 RAG 第一版先做 BM25，没有直接上向量数据库？

没有稀疏基线就无法证明 embedding、向量数据库和 Reranker 的复杂度有价值。BM25 在共同设计的小型开发集上接近满分，但冻结语义改写盲测后 Hit@3 只有 66.7%，证明原结果过于乐观。我随后加入多语向量和 RRF；hybrid 只把 Hit@1 从 58.3% 提到 66.7%，Hit@3 和拒答没有改善，最终报告 P50 还从 0.121 ms 增到 19.724 ms。因此默认仍用 BM25。这比“上了向量库”更能说明我用实验决定架构。

## 25. 怎么防止 RAG 引用看起来可靠但内容已经过期？

每个 passage 保存发布机构、原始 URL 和语料快照日期，语料文件还有 SHA-256；答案展示原始链接，不把本地摘要伪装成实时页面。对紧急电话、法规和医疗信息，系统应提醒以官方页面最新内容为准。上线后还需要定期抓取、内容哈希比对、过期告警和人工审核，目前的静态快照不具备这些生产能力。

## 26. 为什么用 RRF，不直接把 BM25 分数和余弦分数相加？

两种分数的量纲和分布不同，线性加权前需要额外归一化与权重校准；6 条文档的数据不足以可靠学习权重。RRF 只依赖各自排名，公式简单、确定、容易审计。它的缺点是会丢失原始分数间距，所以我仍保留 BM25 与 dense 分项分数，并在融合前用各自阈值做候选门控。

## 27. 向量阈值 0.60 是怎么定的，会不会数据泄漏？

我先冻结并哈希盲测集，然后只在原有开发正例和负例上扫描阈值。0.45 的 dense Recall@3 为 100%，但会把签证问题误召回；0.60 让 hybrid 在开发集保持 Hit@3/Recall@3 100% 且负例全部拒答。参数锁定后才对盲测各运行一次，并且没有依据盲测回调阈值。盲测拒答仍只有 62.5%，这正说明开发集校准不能保证分布外泛化。

## 28. 为什么 dense 盲测反而比 BM25 差？下一步怎么办？

当前语料只有 6 个短段落，通用句向量不是为这组中英旅行安全边界训练的；全局 0.60 阈值在安全拒答和跨语言召回之间出现明显冲突。下一步不会继续消费这组盲测来调参，而是扩展语料和新的开发/测试集，对比检索专用多语模型、query/document 指令、top-score margin 或按主题校准，再在召回候选上加入 cross-encoder Rerank。只有新测试集证明综合指标提升才切默认方案。
