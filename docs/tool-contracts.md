# 工具契约

## 天气工具 `get_weather`

### 输入

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `location` | string | 是 | 面向用户显示的地点名称 |
| `latitude` | number | 否 | 与 `longitude` 成对提供，范围 -90 到 90 |
| `longitude` | number | 否 | 与 `latitude` 成对提供，范围 -180 到 180 |

设备坐标优先于文本地理编码。策略层只接受 `TravelRequest` 中来自设备或调用方的坐标，会删除 LLM 计划中自行生成的经纬度。没有可信坐标时，Open-Meteo Geocoding API 提供候选；同名候选无法可靠区分时，工具失败并要求坐标，而不是猜测第一个结果。

### 输出

Mock 与 Open-Meteo 都必须通过同一个 `WeatherObservation` 模型，核心字段包括：

- 原始地点和解析后地点；
- WMO 天气码及可读天气状态；
- 当前温度、体感温度、降水量和风速；
- 观测时间、时区、解析方式、供应商和来源 URL。

回答层只在降水量大于零或天气码表示降雨时建议雨具，避免把固定模板伪装成工具推理。

### 失败语义

- 经纬度必须成对出现且在合法范围内；
- 地名无结果或存在无法消除的歧义时不调用天气预报；
- 超时、HTTP 错误、非法 JSON 和缺字段被归一化为 `WeatherToolError`；
- 状态图只重试一次，仍失败则返回明确的不可用提示，并在 trace 中保留错误，不编造天气。

### 供应商边界

Open-Meteo 用于地理编码和当前天气，无需密钥。当前实现适合个人项目与低流量演示；上线前仍需要缓存、限流、服务条款复核、监控以及可替换的生产供应商。

## 旅行知识工具 `search_travel_knowledge`

### 当前基线

真实模式使用本地官方来源快照，而不是让模型凭参数知识回答安全问题。语料中的每个段落都包含稳定 ID、标题、发布机构、原始 URL、主题和快照日期；正文是对官方页面的简短改写，不复制整页内容。

第一版检索器使用中英文 BM25：英文按单词切分并移除常见停用词，中文使用双字特征并移除少量高频旅行词。输出通过 `KnowledgeSearchResult` 校验，包含查询、检索方法、最低分、快照日期，以及按分数排序且可追溯的 passage。`top_k` 限制为 1–5，低于最低分时返回空结果，回答层明确说明当前知识快照没有足够依据。

### 引用与安全边界

回答层最多使用前两个 passage，并在每段后附原始来源链接。知识快照不等于实时事实，尤其紧急电话、法规和医疗建议仍应以链接中的官方最新信息为准。检索分数只表示相关性，不表示医学正确性，也不能替代专业人员判断。

### 评测

独立中英文正例集统计 Hit@1、Recall@K 和 MRR，库外问题统计拒答准确率。先冻结稀疏检索基线，再引入稠密向量与 Rerank；只有在新增盲测集和难负例上出现可重复增益，才把混合检索写成项目能力。

## 地点工具 `search_poi`

### 输入与查询边界

真实 POI 查询必须提供 `location`、`latitude` 和 `longitude`。可选参数包括半径、最大结果数、类别和偏好，其中：

- 半径限制在 100–5,000 米，默认 1,500 米；
- 返回数量限制在 1–10 个，默认 5 个；
- 类别只能来自餐厅、咖啡馆、博物馆、景点、公园和宗教场所白名单；
- 用户文本不会直接拼接到 Overpass QL，从而避免查询注入和无界数据抓取。

### 输出与证据

Mock 与 Overpass 都通过 `PoiSearchResult` 模型。每个地点包含 OSM 元素 ID、名称、类别、直线距离、估算步行时间、已验证支持项和来源链接；顶层结果包含查询坐标、半径、供应商及 `© OpenStreetMap contributors` 署名。

素食、纯素、清真和无麸质偏好只有在对应 OSM `diet:*` 标签为 `yes` 或 `only` 时才视为匹配。无法由当前标签体系证明的偏好会进入 `unverified_preferences`，回答只能称为候选，不能宣称符合偏好。

### 失败与生产边界

缺少可信坐标、参数越界、供应商超时、限流和非法响应都会失败关闭并进入 trace。公共 Overpass 实例适合低频手工演示，但不作为生产 SLA；生产环境应增加缓存、配额控制、监控，并使用自建 Overpass 或商业地点服务。
