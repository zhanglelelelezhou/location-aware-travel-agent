# 架构与能力边界

## 目标

本项目验证“位置感知旅行请求能否被可靠地拆解为可审计的工具调用”，而不是追求开放域聊天能力。

## 当前决策

### 为什么先做单 Agent

当前任务可以由一个有状态工作流和多个专业工具完成。过早拆成多个 Agent 会引入额外通信、延迟和不可控性，却没有可测量收益。只有当评测证明单 Agent 在任务分解或上下文隔离上成为瓶颈时，才考虑多 Agent。

### 为什么使用 LangGraph

旅行场景需要显式状态、条件分支、失败恢复和未来的人工确认。普通顺序 Chain 很难清晰表达这些控制流；自由循环的 Agent Executor 又不利于限制成本和重试次数。因此选择有界状态图。

### 为什么保留规则 Planner

规则 Planner 不是最终智能层，而是稳定的可复现基线与故障降级路径。LLM Planner 必须在同一评测集上证明泛化收益，并同时报告延迟与 Token 成本，才能替代默认路径。

### 为什么使用结构化输出和一次修复

自由文本计划无法安全地直接执行。LLM 输出先经过 Pydantic Schema 和工具白名单校验；第一次失败时带着验证错误要求模型修复，第二次仍失败则降级。一次修复在可靠性和额外成本之间提供了明确上限。

### 为什么在 LLM 后增加策略层

语义理解允许概率性，而安全与业务不变量必须确定。LLM 生成通过 Schema 的候选计划后，策略层检查行程工具完整性、必填位置和预订确认边界。每项补正都会进入 trace，便于区分模型原生行为与系统兜底，也避免把所有规则都塞进不断膨胀的 Prompt。

### 为什么默认使用 Mock 工具

作品集首先要可复现。地图、天气和模型 API 都可能需要密钥或产生费用，Mock fixture 可以让测试和评测保持稳定。真实 adapter 后续必须通过同一 Tool 接口接入，并与 Mock 使用相同契约测试。

### 为什么位置优先使用设备坐标

地名不是稳定标识。首次真实天气冒烟测试中，“东京”被地理编码为中国江苏的同名地点，证明直接采用第一个搜索结果会产生静默事实错误。当前请求模型支持成对的经纬度，策略层只把请求中可信的设备坐标注入位置相关工具，并删除 LLM 自行生成的坐标；只有缺少可信坐标时才使用文本地理编码，候选有歧义则失败关闭。解析方式和最终地点会进入工具输出，便于审计。

## 当前不宣称的能力

- 默认意图识别是确定性规则；只有显式启用并配置 LLM Planner 才使用模型推理。
- 当前天气可选择 Open-Meteo 实时数据；POI、翻译和知识结果仍是 fixture。
- 当前 20 条开发集和 20 条冻结留出集主要验证意图、工具路径和约束处理，不能代表回答事实准确率。
- 尚未实现长期记忆、MCP、流式输出和生产级可观测性。

明确这些边界是项目可信度的一部分，后续迭代将用评测结果证明能力增量。
